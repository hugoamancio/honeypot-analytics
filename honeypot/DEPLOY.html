Honeypot Analytics · etapa final

Implantação do Sensor

Da instância vazia na Oracle Cloud até o primeiro ataque real chegando no seu banco. Siga na ordem: duas etapas aqui podem trancar você para fora do servidor, e a ordem existe para impedir isso.

A regra que salva o servidor

A partir da etapa 4, mantenha duas sessões SSH abertas ao mesmo tempo. Faça toda mudança na primeira e confirme na segunda.

Se você fechar a única sessão depois de mexer no SSH e algo estiver errado, não existe recuperação: a máquina vira inacessível e o caminho é apagar e recomeçar. A segunda janela custa dez segundos e é a diferença entre um susto e uma tarde perdida.

1

Criar a instância

Console da Oracle → Compute → Instances → Create instance.

CampoEscolha
ImageUbuntu 22.04
ShapeVM.Standard.E2.1.Micro (AMD)
SSH keyGenerate a key pair for me → baixar a chave privada
Duas escolhas sem volta

A região é permanente. Escolha São Paulo ou Vinhedo. Não dá para trocar depois.

Não escolha a forma ARM (Ampere A1). É a mais generosa e por isso vive esgotada — você vai bater em Out of host capacity repetidamente. A E2.1.Micro tem 1 GB de RAM, sempre tem vaga, e sobra para o Cowrie.

A chave privada só baixa uma vez. Perdeu, perdeu a máquina.

2

Conectar

Anote o IP público que aparece na página da instância. No Windows, a chave precisa ter permissão restrita ou o SSH recusa usá-la. 

# restringe a chave a você (uma vez só)
icacls C:\caminho\chave.key /inheritance:r /grant:r "%USERNAME%:R"

# conecta — porta 22 ainda é a sua, o honeypot não existe ainda
ssh -i C:\caminho\chave.key ubuntu@SEU_IP
3

Instalar o Cowrie

Envie os três arquivos do projeto e rode o instalador. Ele sobe o Cowrie em 2222 e 2223 e não toca na porta 22 — nada de trânsito da internet ainda. 

# da SUA máquina, envia os arquivos
scp -i chave.key honeypot/cowrie.cfg honeypot/userdb.txt honeypot/instalar.sh ubuntu@SEU_IP:~/

# já no servidor
chmod +x instalar.sh
./instalar.sh

Leva uns 5 minutos. No fim aparece COWRIE NO AR com as portas.

4

Mudar o seu SSH de porta

Abra a segunda sessão agora

Antes de digitar qualquer coisa desta etapa, abra outra janela e conecte de novo no servidor. Ela é a sua rede de segurança e só pode ser fechada no fim da etapa 5.

O truque que elimina o risco: o SSH vai escutar nas duas portas durante a transição. Só removemos a 22 depois de confirmar que a 2200 funciona. 

# 1. libera a 2200 no firewall do Ubuntu, ANTES de tudo
#    veja onde está a regra REJECT e insira antes dela
sudo iptables -L INPUT --line-numbers | head -12
sudo iptables -I INPUT 6 -p tcp --dport 2200 -m state --state NEW -j ACCEPT
sudo netfilter-persistent save

# 2. faz o sshd escutar nas DUAS portas
sudo sed -i 's/^#*Port 22$/Port 22\nPort 2200/' /etc/ssh/sshd_config
sudo sshd -t          # valida a sintaxe — se der erro, PARE
sudo systemctl restart ssh

Agora, no console da Oracle, abra a porta na rede: Networking → Virtual Cloud Networks → sua VCN → Security Lists → Default → Add Ingress Rule — origem 0.0.0.0/0, TCP, porta 2200. 

# 3. da SUA máquina, numa TERCEIRA janela, teste a porta nova
ssh -i chave.key -p 2200 ubuntu@SEU_IP
Ponto de decisão

Entrou pela 2200? Siga. Não entrou? Não feche nada — volte na sessão que ainda está aberta e desfaça: o problema é quase sempre a regra do Security List ou a posição da regra no iptables.

5

Entregar a porta 22 ao honeypot

Só faça isto com a 2200 confirmada. Agora removemos a 22 do seu SSH e redirecionamos para o Cowrie. 

# 1. sshd deixa de escutar na 22
sudo sed -i '/^Port 22$/d' /etc/ssh/sshd_config
sudo sshd -t
sudo systemctl restart ssh

# 2. tudo que chegar na 22 vai para o Cowrie (2222); na 23, para 2223
sudo iptables -t nat -A PREROUTING -p tcp --dport 22 -j REDIRECT --to-port 2222
sudo iptables -t nat -A PREROUTING -p tcp --dport 23 -j REDIRECT --to-port 2223

# 3. libera as portas do honeypot no firewall
sudo iptables -I INPUT 6 -p tcp --dport 2222 -m state --state NEW -j ACCEPT
sudo iptables -I INPUT 6 -p tcp --dport 2223 -m state --state NEW -j ACCEPT
sudo netfilter-persistent save

No Security List da Oracle, adicione ingresso 0.0.0.0/0 TCP para as portas 22 e 23.

De agora em diante

Você entra no servidor pela porta 2200. A porta 22 pertence ao honeypot — conectar nela te leva ao sistema falso, o que rende uma confusão memorável às duas da manhã.

6

Confirmar que está pegando

# acompanhe ao vivo — os primeiros bots costumam chegar em minutos
tail -f ~/cowrie/var/log/cowrie/cowrie.json | jq -r \
  '"\(.timestamp)  \(.src_ip)  \(.eventid)  \(.username // "")/\(.password // "")"'

Se em uma hora não apareceu nada, o problema é quase sempre o Security List. Teste de fora com ssh -p 22 teste@SEU_IP — deve pedir senha (e é o Cowrie respondendo).

7

Trazer para o banco

Na sua máquina, com o Docker e o Postgres de pé: 

.\honeypot\coletar.ps1 -Ip SEU_IP -Chave C:\caminho\chave.key

O script baixa o log, ingere e roda as regras. Nenhuma linha do pipeline muda — o formato é o mesmo do gerador sintético, que foi exatamente o motivo de ele existir.

Antes da primeira coleta real

Limpe os dados sintéticos, senão as duas fontes se misturam e nenhum número do README significa mais nada: 

docker exec honeypot_db psql -U analista -d honeypot \
  -c "TRUNCATE origem, credencial, arquivo_processado RESTART IDENTITY CASCADE;"
8

Higiene do servidor

  • Nada seu na máquina. Sem arquivos pessoais, sem chave que sirva em outro lugar. Ela é descartável por definição.
  • Senha desativada no seu SSH. Só chave — PasswordAuthentication no no sshd_config.
  • Atualize. sudo apt update && sudo apt upgrade de vez em quando.
  • Olhe o disco. O log cresce rápido; df -h semanalmente evita surpresa.
  • Nunca execute o que os bots baixam. O Cowrie guarda os artefatos em var/lib/cowrie/downloads — são malware de verdade. O projeto grava apenas o hash, nunca o conteúdo.
